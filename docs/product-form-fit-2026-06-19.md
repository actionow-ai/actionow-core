# 产品形态契合度分析（2026-06-19）

> 目标场景：① 把 actionow-core 当**开箱即用后端/SDK** 嵌进开发者自己的应用（其客户=租户）；② 把 actionow-core 当**模型中转站直接运营**（终端客户自助注册成租户）。
> 本文判断当前产品形态是否契合这两种场景，并给出前后端协同的调整方向。配套：[设计评审](./frontend-design-review-2026-06-19.md) · [接口接入盘点](./backend-wiring-and-dev-plan-2026-06-19.md)。

## 核查到的关键事实（代码为准）

1. **没有 SDK 包**：`packages/` 下无 `sdk`/`client`；唯一的 TS 客户端焊死在 `apps/web/src/lib/api` 里，外部不可消费。
2. **管理端鉴权只有人工 JWT**（`POST /admin/auth/login` → 验 `ADMIN_JWT_SECRET`），**没有 service-token / API-key 的机器对机器（M2M）通道**。
3. **自助注册会自动建 tenant + account + user**（`createTenant({name: 'user-<email>'})`）——自助 onboarding 链路存在，注册即「1 用户 1 租户」。
4. **用户模型支持「一个租户多用户」**（`user.tenant_id` + `role` user/admin），但 `/app` 没有团队/成员管理 UI。
5. **品牌是 `t('brand')` + 硬编码六边形 SVG**，非按部署运行时白标配置。
6. **Landing 硬挂在 `/`**，无开关禁用/替换；它营销的是「Actionow，自部署你自己的网关」——即把 actionow 卖给运营方。

## 核心矛盾

actionow-core 是**一个可部署物**，却把**三类受众**焊在一起：

- **(M) 营销** —— Landing，卖 actionow 给运营方；
- **(O) 运营方** —— 管理控制台 `/console`；
- **(T) 租户** —— 自助控制台 `/app` + relay API `v1/*`。

**问题不在三个面的划分**（这个架构对两种场景都对），而在于**它们被焊成一个带硬编码 Actionow 品牌、且营销页常驻的单体**。修复方向是**可配置化 + 拆包**，不是重新设计。

## 按场景的契合度

### 场景 ② 直接运营中转站 —— 🟡 骨架契合，差「解耦 + 完善」

- ✅ 自助注册→自动建租户+账户 = 自助漏斗已通；`/app`（概览/用量/Key/计费/模型/设置）+ `/console`（目录/渠道/定价/租户/中转审计）基本齐全。
- ❌ **Landing 是「错的营销」**：运营方部署后，他的客户访问 `/` 看到的是 actionow 自我营销，而不是运营方自己的「买 AI 额度 / 用我的 API」着陆页。
- ❌ **缺开发者上手面**：场景②的客户是开发者，需要 base_url + 复制即用的 curl/SDK 片段 + 「你的第一个调用」。现在 Key 与模型分散、无「怎么调」引导（呼应评审「AppModels 过薄」「改个 base_url 就能接入」）。
- ❌ 计费充值需完善（真二维码、充值页显余额）；relay 仅文本 chat（多模态是示意）。

### 场景 ① 当后端/SDK 嵌入 —— 🔴 目前不契合，「SDK」名不副实

- ❌ **没有可消费的 SDK**：actionow-core 是「自部署后端平台」，不是 `npm install` 进你后端的库。要嵌入，开发者得自部署整套服务，再对着 HTTP API 自己写客户端。
- ❌ **没有 M2M 凭证**：场景①里开发者的后端要在客户注册时**程序化建租户/账户/Key**，但 admin 只认人工 JWT——只能塞 admin 账密（危险）或手动转 JWT。
- ❌ **`/app` 不是可嵌入/白标的 widget**：开发者要么用 actionow 的品牌 UI，要么完全自建前端（但又没有 SDK 帮他建）。
- ✅ 底层数据模型（租户/账户/Key/账本/RBAC）是对的，能力都在——**缺的是「对外交付物」的形态**。

## 前后端协同建议（按杠杆排序）

> 这些是**产品形态层**的调整，部分应优先于设计评审的 P3/P4 打磨项。

1. **拆「营销」与「产品」**（FE + infra）：给 `/` 加部署模式开关——`marketing`（actionow.com）vs `app`（已部署实例）。已部署实例不应自带 actionow 营销页：默认把 `/` 重定向到 `/login` 或运营方可替换的模板。**两个场景都受益**。
2. **真·客户端 SDK**（BE/打包，**场景① 的命门**）：把 `apps/web/src/lib/api` 抽成 `packages/sdk` 发布（TS 先行，再 Python），同时覆盖 `console/*`（租户向）与 `admin/*`（供给/运营向）。现在的 in-app client 已是 80% 的 TS SDK。
3. **M2M 管理凭证**（BE，**场景① 必需**）：给 `AdminGuard` 增加 service-token / admin-API-key 通道（与 JWT 并存），让开发者后端无人值守地调用 `admin/*` 供给租户。
4. **运行时白标配置**（FE + BE）：品牌（名称/Logo/`--accent` 主色/支持链接）走运行时配置（env → `/console/config` 或 `window.__APP_CONFIG__`），免 fork 改 i18n/SVG。设计系统已是 token 化，天然支持。**两个场景都受益**。
5. **开发者上手面**（FE）：`/app` 加「Quickstart / 集成」面——base_url + 新建 Key + 复制即用的 curl / OpenAI / Anthropic 片段 + 可用模型。场景②客户与场景①终端用户的「第一个调用」入口。
6. **供给链路双轨化 + 一步供给**（BE）：明确并文档化两条供给路径——自助注册（场景②）vs 管理端供给（场景①）；为场景①加一个 admin「一步供给一个客户」端点（tenant + account + 初始 Key 一次返回）。
7. **租户团队（多用户）UX**（FE，较低优先）：schema 支持一租户多用户，但 `/app` 无成员邀请/管理；当「租户=组织」时需要。

## 并入现有开发计划

在之前的 P0–P4 之上，**插入一档「P1.5 产品形态对齐」**（部分应抢在 P3 设计系统重构之前）：

- **P1.5-A 解耦与白标**（建议 = 高）：部署模式开关（#1）+ 运行时品牌配置（#4）。低风险、解锁两个场景的「可交付」。
- **P1.5-B 场景① 使能**（建议 = 高，若场景①是真目标）：抽 `packages/sdk`（#2）+ M2M 管理凭证（#3）+ 一步供给端点（#6）。
- **P1.5-C 上手体验**（建议 = 中）：开发者 Quickstart 面（#5）。
- 团队管理（#7）随后。

**一句话**：三个面的划分是对的，骨架对场景②基本可用、对场景①明显不足。差距集中在**「把单体拆成可配置、可嵌入、可程序化供给的交付物」**——这是打包/配置/凭证层的活，不是 UI 重画。建议**先做 P1.5-A（解耦+白标）**，它对两个场景都是地基；若场景①确为目标，紧接 **P1.5-B（SDK + M2M）**。
