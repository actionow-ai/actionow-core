守卫保护规则要点
AdminGuard/admin/*登录 JWT 验 ADMIN_JWT_SECRET，或 at_* 服务令牌验 admin_token；拒 typ:subject；@Roles 强制

💳 资金与钱包

account（租户钱包，1:1）持 credit_balance / credit_held；可选 sub_account（端用户 HARD 钱包）覆盖租户池，缺省则共享（SHARED）。原子条件更新 balance − held ≥ amount 防超卖；每 job 仅一条结算（partial-unique index）。

🧾 记录三件套

ledger_txn 资金真相源（仅追加，不可变）· usage_log 每次调用一行（best-effort 镜像）· relay_trace 上游报文留痕（无 FK，密钥脱敏）· audit_log 变更轨迹（actor/action/target）。

🗂️ 目录与路由

resource（slug 主键）→ model / upstream_channel（多对多经 channel_model）。route_group 携 group_ratio_bps 与自引用 fallback_group_id；成员经 route_group_channel（priority / weight）。

🛡️ 治理

limit_plan（tenant_id 为空 = 平台级）打包 limit_rule（维度 × 周期），绑定到 key / account / subject；limit_usage 累加器 + limit_alert 阈值告警（同维度仅触发一次）。

06

中继请求数据流一次 LLM 调用的全过程

认证 → 治理预检 → 模型/通道解析 → 持有额度 → 故障转移结算流 → 结算一次 → 镜像观测。 结算在 finally 中幂等地只发生一次；流式持有为「慷慨上限」，结算永不超过持有额度。 

sequenceDiagram
  autonumber
  participant C as Client app
  participant AK as ApiKeyGuard
  participant GV as GovernanceGuard
  participant RS as ChatRelayService
  participant RT as ChannelRouting
  participant BR as Breaker (Redis)
  participant EX as SettlingStream
  participant AD as Adapter
  participant UP as Upstream
  participant DB as Wallet + Ledger (PG)

  C->>AK: POST /v1/messages (ak_*, IR, route-tag, idem-key)
  AK->>AK: sha256 lookup, resolve tenant / subject / account
  alt 无效 key / subject 失活
    AK-->>C: 401
  end
  AK->>GV: ApiKeyContext
  GV->>GV: RPM + 并发 (Redis) + limit_plan (key ∪ tenant ∪ subject)
  alt 超额度
    GV-->>C: 429 (rpm/并发) / 402 (spend/tokens/requests)
  end
  GV->>RS: TenantContext
  RS->>RS: 解析 model→resource, 归一化 IR
  RS->>RT: candidatesFor(resource, group, model, tag)
  RT-->>RS: 有序 RunChannel[] + group_ratio_bps
  RS->>DB: holdCredits (HARD 则 sub_account, 否则租户池)
  alt 余额不足
    DB-->>C: 402 insufficient_credits
  end
  RS->>EX: createChatSettlingStream
  loop 跨通道 / 跨 fallback 组 故障转移
    EX->>BR: availableChannels (排除 Open, 半开试探)
    EX->>AD: streamChat (容错策略超时)
    AD->>UP: HTTP (代理, 签名)
    alt 首事件成功
      UP-->>AD: 流
      EX->>BR: 记成功

      EX->>BR: 记失败 (冷却) → 下一通道
    end
  end
  EX-->>C: SSE 增量 (按方言渲染)
  EX->>DB: 结算一次 — 扣最终费, 追加 ledger_txn settle

  EX-->>C: done {jobId, usage, cost.credits}

模型降级链（模型降级）仅限中继、仅阻塞式、仅可重试错误；每次尝试用独立幂等键 ${orig}:fb${i}。流式无模型降级——一旦中途提交即不可换模型。

路由与弹性通道怎么选、坏了怎么办

三层防御：同通道容错策略重试 → 熔断感知的跨通道/跨组故障转移 → 每(通道,模型) 熔断 FSM。失败开放（fail-open）：熔断器自身故障绝不阻断请求。

熔断状态机（弹性2.0 · 每「通道 × 模型」）

stateDiagram-v2

🔁 容错策略 fault_policy

fastFail · retryCount · backoffType（fixed|exponential，×2^(n-1) 上限 60s）· 每尝试 connect/TTFT/total/idle 超时（经 wrapHttpWithTimeouts）· retryCodes/retryMessages 触发器。

🏷️ 路由染色 / 标签路由

X-Actionow-Route-Tag 仅收窄候选集（绝不放宽）；无匹配硬 400，杜绝静默泄漏到未打标通道。标签记入 relay_trace 与 usage_log 供金丝雀聚合。

ledger_txn 是唯一真相源（仅追加、不可变）；balance_after 在同一事务里经 UPDATE…RETURNING 读出。 同一张表承载内部成本分摊（subject_id=null，租户级）与对外营收（subject_id=uuid，端用户级）。

注记与待确认诚实标注：图中哪些尚未在代码中坐实
